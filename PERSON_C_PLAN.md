## 1. Mission

Build the judge-facing evidence viewer and report presentation layer for Behavior Review.

The result must make one real run easy to understand:

1. What changed?
2. What caller outside the diff could be affected?
3. What did the same input produce on base and head?
4. What is still unknown or inconclusive?
5. What human decision is required?

The UI explains evidence. It does not invent evidence, run arbitrary code, or decide whether a change is a bug.

## 6. Minimum UI-facing report contract

A owns the authoritative shared schema. This is the minimum information C needs to render the page and must be confirmed with A, B, and D before the real integration.

```json
{
  "schema_version": "0.1",
  "fixture": true,
  "run": {
    "repo": "owner/repo",
    "base_sha": "abc123",
    "head_sha": "def456",
    "generated_at": "2026-09-26T12:00:00Z",
    "status": "complete"
  },
  "changed_symbols": [],
  "impact": {
    "paths": [],
    "unknowns": []
  },
  "observations": [],
  "decisions": [],
  "limits": [],
  "links": {
    "action_run": "",
    "artifact": ""
  }
}
```

The adapter must tolerate additional fields and missing optional fields.

### Expected outcome labels

- `same_on_tested_cases`
- `delta_observed`
- `inconclusive`
- Existing test results must remain separate from behavior outcomes.

### Expected decision labels

- `unintended`
- `intended`
- `unresolved`

An intended decision requires a non-empty rationale in the UI. Visitor decisions remain in memory only and are never approvals.

## 7. Visual direction

### Design read

A trust-first engineering evidence viewer for technical judges, using IBM/Carbon precision and a restrained audit-dossier language.

### Design dials

- Design variance: 4
- Motion intensity: 2 to 3
- Visual density: 5

### Visual rules

- Neutral surfaces with one primary blue accent
- Semantic colors only for real states such as delta, inconclusive, or resolved
- Strong hierarchy for evidence, paths, hashes, inputs, and outputs
- Minimal gradients and shadows
- Consistent radius and spacing tokens
- Code values use a readable monospace face
- Do not build fake terminal windows or fake product screenshots
- Do not hide important limitations below the fold
- Do not use decorative status dots without semantic meaning
- Support keyboard navigation and visible focus
- Support light and dark themes without changing meaning
- Respect `prefers-reduced-motion`

Use `tasteskill.dev` as a visual reference only. It is not a runtime dependency and its assets must not be copied.

## 8. Page information architecture

### Run header

Show:

- Product label, temporarily `Behavior Review`
- Run status
- Repository
- Base and head commit identifiers
- Generated time
- GitHub Actions link when available
- Fixture label when the source is not real

### Evidence summary

Use plain language and real counts:

```text
1 behavior difference observed
1 caller found outside the changed file
Existing tests passed
```

Do not present passing tests as proof of safety.

### Impact path

Show a readable path such as:

```text
pricing.discount.apply_discount
        |
        v
pricing.invoice.price_total
```

Each node should include relative path, symbol, and line number when available. Mark callers outside the diff clearly. Unknown edges must be a separate visible state.

### Behavior comparison

For every observation show:

- Probe name or identifier
- Input
- Probe hash
- Base output or exception
- Head output or exception
- Outcome label
- Timeout, import, or setup details when applicable

Use expandable details for raw JSON so the main view stays readable.

### Human decision panel

The panel must explain:

```text
This decision is session-only. It is not saved to the repository and does not approve the change.
```

Behavior:

- `Unintended`: records a temporary local selection
- `Intended`: requires a rationale
- `Unresolved`: keeps the issue prominently open
- Reloading the page resets the visitor selection

### Limits panel

Show:

- Bounded impact analysis
- Tested inputs are not all possible inputs
- Unknown edges are not proof of safety
- Setup failures are inconclusive
- Human intent does not override failed execution

## 11. Test matrix

### Data states

- Complete run with `delta_observed`
- Complete run with `same_on_tested_cases`
- Import/setup failure with `inconclusive`
- Unknown impact edge
- Both revisions fail
- Missing optional Action link
- Malformed or missing report JSON

### Interaction states

- Intended without rationale is blocked
- Intended with rationale is shown as session-only
- Unintended selection is shown as unresolved until the next real run
- Unresolved remains prominent
- Reload clears the temporary decision

### Visual and accessibility checks

- Desktop viewport
- Narrow mobile viewport
- Light theme
- Dark theme
- Keyboard-only navigation
- Reduced motion
- Readable focus state
- Sufficient text and control contrast
